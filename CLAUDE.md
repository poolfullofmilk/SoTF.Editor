# SoTF Editor

A savegame editor for Sons of the Forest. A WPF window hosts a `BlazorWebView` whose whole UI is MudBlazor, laid out like `WiFiWatch`. It reads a savegame folder, lets people edit it page by page, and writes back only what changed, after a verified copy of the whole savegame.

| Project | Holds |
|---|---|
| `SoTF.Editor.Data` (`net10.0`) | Savegame and game data models, view models, enums, helpers (`AppInfo`, `SaveJson`, `Formatter`, `LoadedValues`, coordinates), and `Resources`: the resx text, `TextKeys`, `GameNames.resx`, the embedded `GameData.json`, `Pois.json`, `ItemPois.json` and `ActorTemplate.txt` |
| `SoTF.Editor.Services` (`net10.0`) | `Savegames` (finding, loading, saving, backups, `MainViewModel`), `Pages` (one view model per page), `Actors`, `Map`, `Tools`, `Settings`, `Integration` (update check and updater) |
| `SoTF.Editor.Desktop` | `App` (startup, logging, single instance, DI), `MainWindow` (WebView2 host), `Components`, `Theming/AppTheme`, `Interop` (`LocalFiles`, `WindowCaptionTheme`), `wwwroot` |
| `Tests` | `SaveRoundTrip.cs`, a file-based app, and `Sample`, the savegame it edits |

Packages: MudBlazor, `Microsoft.AspNetCore.Components.WebView.Wpf`, Newtonsoft.Json, NLog. No MVVM toolkit, no Bootstrap, no tray: the editor has no background work, so closing it exits.

## Build, Run And Publish

```bash
dotnet build SoTF.Editor.slnx
```

```bash
dotnet run --project SoTF.Editor.Desktop
```

```bash
dotnet run Tests/SaveRoundTrip.cs
```

```bash
dotnet publish SoTF.Editor.Desktop -c Release
```

The publish folder holds only `SoTF.Editor_v<Version>.exe`: `IncludeAllContentForSelfExtract` and the `BundleWebRoot` and `RemoveLooseWebRoot` targets pack `wwwroot` inside it.

The Release exe is ReadyToRun (`PublishReadyToRun`), so MudBlazor and the editor's own code start compiled: 102 MB instead of 79, and on a Linux host build the first page opened 100 to 500 ms sooner, the first Inventory about 100 ms and the first Map about 50 ms; other pages opened as fast either way. The bundle unpacks once (`IncludeAllContentForSelfExtract`), so the bigger files cost nothing after the first start.

`.github/workflows/build.yml` builds the solution in Release and runs `Tests/SaveRoundTrip.cs` on `windows-latest` for every branch push and pull request; only a tag releases.

### Releasing

Versions take a third number. A fix or a small change ships as a patch (`3.4.1`, then `3.4.2`); only a release with new features or reworked pages bumps the minor (`3.5`). Try the patch first. The update check, the exe name and the tag all handle three parts.

A release is made by the workflow, not by hand, the way `WiFiWatch` does it. `.github/workflows/release.yml` runs `Tests/SaveRoundTrip.cs`, publishes the exe on a `v*` tag and creates the release `SoTF Editor v<Version>` with the exe as its only file. Unlike other projects the body is not empty: it lists the commit titles since the previous tag (`fetch-depth: 0`, `git describe` on `<tag>^`), and the update dialog of a build without its commit shows them under What Changed (a workflow build lists every commit since itself, see Updates). So commit titles are what users read, and they never say Release or a version number: the tag already says it, and the title would repeat it in the notes.

1. `git pull`, the owner edits the README on GitHub.
2. Bump `<Version>` in `SoTF.Editor.Desktop.csproj` first, so the Debug build is not older than the latest release and shows no update dialog or badge. Then retake all ten screenshots from a copy of a real savegame (hash the real `Saves` first and compare after), copied with `cp -rp` and `touch -r` on the folders so its card keeps the real save time, into a generic folder such as `C:\Saves` that the Debug settings point at: the Savegames page and the cards' hover titles show the folder, and a scratchpad or profile path names the owner (`C:\Users` itself needs admin rights). Before each shot, check that no text or attribute on the page names the owner or the scratchpad. The Debug backups of that save id fill the Restore Backup shot, so nothing needs saving. The shots: `Overview.png` (Player), `Inventory.png`, `Storage.png` (Arrow Holder #1 selected), `Followers.png`, `Game.png` (setup tab), `Npcs.png` (Baby selected), `Structures.png`, `Map.png`, `Tools.png` and `Backups.png` (Restore Backup with a row selected). Over CDP: `Emulation.setDeviceMetricsOverride` with `1600 x 845` at scale `1.6` gives LetsWatch's `2560 x 1352`. The README keeps every shot for its last section, Screenshots: one column, each under a small title (the owner's pick, so the features come first and no grid sends people clicking through files).
3. Update the README for what shipped, publish, and launch the exe alone from an empty folder. The installed copy holds the single-instance handle, so close it first. The README stays short, the owner's pick: no tagline or picture under the title, and one short plain bullet per feature that says what it does, never its details, which the app explains itself.
4. Commit, push, then `git tag v<Version>` and `git push origin v<Version>`. The tag must match `<Version>`, the workflow looks for `SoTF.Editor_v<tag>.exe`.
5. Once the new release is live, delete the previous one with its tag: `gh release delete v1.0 --yes --cleanup-tag`. Not before: the new run needs the previous tag for its notes.

## Where Data Lives

| What | Where |
|---|---|
| Settings (`UserSettings`) | `%AppData%\SoTF.Editor\settings.json` |
| WebView2 profile | `%AppData%\SoTF.Editor\WebView2` |
| Logs | `Documents\SoTF.Editor\Logs` |
| Backups | `Documents\SoTF.Editor\Backups\<steam id>\<SinglePlayer or Multiplayer>\<save id>\<yyyy-MM-dd HH-mm-ss>` |
| Unlocks backups | `Documents\SoTF.Editor\Backups\<steam id>\<file name>\<yyyy-MM-dd HH-mm-ss>` |
| Real savegames | `%UserProfile%\AppData\LocalLow\Endnight\SonsOfTheForest\Saves\<steam id>\<mode>\<save id>` |
| The game's own backups | `<save id>_backup_<yyyyMMddHHmmss>.zip` beside the save folder, one per in-game save; the editor ignores them |
| Test sample | `Tests\Sample\76561190000000000\Multiplayer\1000000001`, a real save with a made-up Steam id and no thumbnail, so its card shows the placeholder |

A Debug build uses `SoTF.Editor Debug` for all of these folders (`AppInfo.FolderName`), so a test run never mixes with the installed app.

`Multiplayer` saves are games the player hosted. A `MultiplayerClient` save is a game they joined on someone else's server: it holds only their own player, the world lives in the host's save. The Savegames page groups them as Hosted Multiplayer and Joined Multiplayer, with an info button on the joined group. A joined save has no `.name` file, no thumbnail and nothing about the host or lobby (checked on two real joined saves: only game type, days, crash site, save time and a game id), so its card is titled like the game names hosted saves (`Hard 15 Days`, `JoinedGameName`) and shows a people icon instead of a picture.

## Saving

**Never edit a real savegame.** Copy the savegame with its parent folders into the scratchpad and point **Savegames → Change** at the copy.

- Every page view model has `Load(Savegame?)` and `Update(Savegame)`. `MainViewModel.SaveChanges` runs every `Update` in a fixed order (setup, state, weather, inventory, armour, followers, player, storage, structures); each marks the `SaveDataWrapper` it changed.
- `SavegameStore` writes only modified wrappers. `MainViewModel.SaveChanges` checks the loaded files still exist and makes the backup (`SavegameStore.BackUpLoaded`) before any page merges, so a failed save leaves the open copy as it was and Revert Page still undoes its edits; only a write failing midway leaves merged edits behind. It saves nothing while `HasUnsavedChanges` is false. `BackupManager.Create` first copies every file of the savegame and compares each copy byte for byte; if that fails, nothing is written. Loose files are written to a temp file and moved over; `SaveData.zip` is updated on a copy that then replaces it. A changed file with neither a loose copy nor the archive left fails the save before the backup. The modified flags clear only after every file is written, so a failed save can be retried.
- A backup whose copy fails deletes its dated folder, so it never shows up as one to restore (`BackupManager.NewBackup`).
- Save asks before overwriting outside changes (`SavegameStore.HasChanged`): it compares every file's name, size and write time with the load, because a file rewritten in place leaves the folder time alone. The warning says saving can undo the progress the game just saved. A Savegames card opens a fresh `Savegame` (`Home.Open`), not the one read when the list was built, or its stamp is old and the warning fires for nothing.
- A save with no edits says **No Changes** and writes nothing. A rewrite on a no-op save is a bug, and `Tests/SaveRoundTrip.cs` fails on it.
- `SaveDataWrapper` keeps each nested document as it was loaded and only counts a marked document that now differs (`JToken.DeepEquals`). So an edit undone, or a tool that finds nothing to change, writes nothing, and the close prompt only asks about real changes.
- Restore lists the backup's files first, so a missing or empty backup fails before anything is touched. It copies the current files to a safety backup, then copies the chosen backup back and removes files the backup lacks (the game renames the `.name` file on every save). **Backups → Restore Backup** lists them newest first (`BackupManager.List`) like the NPC list: an inset `panel-flush` list of `list-row` rows, each with its time and a caption of its size and Newest or Oldest; clicking the picked row again unpicks it. The menu item is disabled while the savegame has no backup (`BackupManager.Count`).
- A save through the Save Changes dialog writes that dialog's list into the backup it made (`SoTF.Editor.Changes.json`, `BackupManager.ChangesOf`); the Item Plater writes its own line, and a restore writes Restored Backup From into the safety backup it makes (`BackupManager.RestoreKey`), so that backup never reads Not Recorded. Restore is disabled while the picked backup is the same as the save now. Restore never copies that file back, and a damaged or missing one reads as not recorded. A picked backup shows Saved After This Backup (that list, grouped by page like the Save dialog through the shared `ChangeList`) and Differs From Now (`BackupDiff.Describe` on the thread pool, grouped by page like the saved list: `BackupManager.DifferingFiles` finds every loose file and `SaveData.zip` entry that differs by SHA-256, the `.name` file by its name, then each document a page shows is compared entry by entry and named the way that page names it: settings and world object states for Game, stats, armour and outfit for Player, items for Inventory, actors by type for Followers and NPCs with their memories, numbered storages for Storage, structures by type, ziplines for Map; repeats read once with their count greyed on the right (`Change.Count`), and files no page shows, or that differ outside those documents, list under Other Files). **Delete Backups** sits left of Restore and switches the list to picking: rows show a checkbox, the newest a lock (it always stays, so the last save can be undone), the changes hide, and the actions become Back, All But Newest and Delete N, which asks and deletes each through the guarded `BackupManager.Delete`; a folder that fails is skipped and reported.
- **Revert Page** (an `Undo` icon inside a page's menu button on the right, shown while that page has edits it can take back, positioned by `nav-action`) takes that page back to its load after showing what goes back (`SaveChangesDialog` with `Revert`: that page's change list and a Revert button): every page with a menu dot has one. Player, Inventory, Storage, Game and Structures keep edits in memory until Save, so `MainViewModel.RevertPage` just reloads their view models. Followers, NPCs, Map and Tools change the open JSON at once, so their revert puts back their part of it from the copy `SaveDataWrapper` kept at load (`LoadedCopy`, `Revert`): `JsonModifier.RestoreEntries` restores the entries a page owns by unique id and keeps every other entry, edited, in place and as the same token. Followers own the follower actors, their memories, carried items, kill stats and death flags; NPCs every other actor with its memory, items and the spawners; Map the zipline document and the zipline structures (id 55) by position; Tools the documents only tools touch (fires, traps, damage, world items, trees, the player state) plus, only after Cannibal Anger or a Game State tool ran, the cannibal memories, kill stats and world counts or the Game State values. Storage keeps its picked storage by position, and a tool whose only change was reverted loses its dot.
- Backups are capped at `BackupManager.SizeLimit` (500 MB, no picker). After each new backup, `Prune` deletes the oldest until the total fits, but every savegame keeps its very first backup and the one just made. `Pruned` raises a warning snackbar in `MainLayout`, and the restore dialog shows the usage, measured once when it opens and lowered by each delete. Restore prunes only after copying back, or it could delete the backup it is restoring. A folder that fails to delete is skipped, saving never fails over it. `BackupManager.Delete` only removes a dated folder inside the backups folder.
- Save first shows `SaveChangesDialog`: the pages with a menu dot, each with its menu icon and a line per change under it (`SaveChangesDialog.ChangesOf` from each page's `ChangedNames` or `Changes`: stat names, armour pieces, items, storages, followers by copy, setting labels, NPC types, structures, ziplines, tools; six at most, then an underlined And N More link that opens every change in `ChangesDialog`, the same in the Restore Backup dialog). Each line leads with its mark in a 20 px box: a green plus for something added, the amber dot for a change, a red minus for something removed (`Change`, `ChangeKind`), and a repeated change (NPCs of one type) reads once with its count greyed at the right end of the line; Armour, Inventory, Followers and NPCs tell the three apart, other pages only change, and a spawned follower copy shows only in its Copies line, a note that a backup is made first, and a filled Save button (the X cancels). Save is disabled while `MainViewModel.HasUnsavedChanges` is false, so a no-op save never shows a snackbar. With no dot but a changed store it saves straight away and the store decides.
- A savegame that fails to load (damaged JSON) closes itself in `MainViewModel.SelectSavegame`, so no caller leaves a half loaded page: open, reload, restore, the language switch and the Item Plater. Open, reload and restore fail through `MainLayout.TryBusyAsync`, which logs the exception and shows a snackbar with **Open Backup Folder**, because the closed savegame disables the Backups menu; a failed restore keeps its safety backup there. Open, reload, save and restore run through `MainLayout.RunBusyAsync`: it shows the busy overlay and yields once, so the overlay paints before the blocking work.
- The Item Plater writes at once (`MainViewModel.SaveWrappers`), so it asks to discard unsaved edits and reloads before plating. A failure shows Unable to Save and keeps the dialog open.
- Closing the window with unsaved edits asks first (Close Without Saving, saying what Yes and No do on three lines: the question, then Yes, then No, no blank line); Windows shutting down never waits for it. The in-app Discard Unsaved Changes question reads the same way, because `.mud-message-box` keeps the line breaks of its text (`white-space: pre-line`). That check (`MainViewModel.HasUnsavedChanges`) asks every page and the store, never merges: a merge for asking wrote the edits into the open copy, so after a declined discard Revert Page restored them and a Structures row set back to None was still removed on save.
- Anything that changes actors goes through `MainViewModel.ModifyActors`: it writes unsaved follower edits into the JSON first, runs the change, then reloads followers and NPCs.
- Removing NPCs drops their influence memory and carried items (`NpcItemInstances.ActorItems`), as removing a follower copy does. The actor dialog edits copies of the influences, so closing it without Apply changes nothing.
- A new follower (Spawn, or Revive of one the game deleted) appears at `MainViewModel.ArrivalPosition`: the player, or while the player is underground a living follower on the surface, because followers cannot follow into caves. Move to Player, Spawn and the map's Bring to Player stay clickable when a cave blocks them and say why in a warning snackbar (`FollowersStayOutside`, `NoArrival`), so a greyed button never leaves people guessing. The Followers page has no Move to Kelvin or Virginia (the Player page keeps them for the player). A map teleport of Kelvin or Virginia moves every copy, a step apart, and is disabled while none is in the save. An actor point on the map has **Bring to Player**: a follower moves like Move to Player, any other actor goes through `ModifyActors` with the NPC dialog's NPC to Player.
- The game deletes a dead follower's actor some time after death and keeps only `IsVirginiaDead` or `IsRobbyDead` (seen in a real save: Virginia gone between autosaves). The panel then shows Dead with no Unique ID, and Revive creates the follower anew (`FollowerModifier.Revive`), so it counts a missing follower marked dead as revivable.
- The game leaves out values that are `0` or `false`, so a missing field reads as its default, never as an error. The Game State and Weather tabs list every known field even when the save lacks it (a spring save has no `_currentSeason`), and `GenericSetting.MergeTo` adds a missing field only for a non-default value. The Player page does the same for a stat, strength, position or area the save left out (`PlayerPageViewModel.AddMissingEntries`, `TargetHealth` with `CurrentHealth`): an edit of a missing stat used to be lost on save.
- The player's cave or bunker is the `player.areaMask` entry (`IntValue`); followers and NPCs carry a `GraphMask`. Moving a follower writes both its position and its graph mask.
- A storage keeps every slot the save holds, even past its definition: stone holders now hold two stacks, and dropping the extra one lost items on every save.
- A stored item writes its loaded `UniqueItems` back untouched (food timers, actor seeds); only a changed count or item builds new ones (`StoredItem.UniqueItemsToSave`). A food storage swaps a food module only for another food state (`IsEqualTo` on `CurrentState`); comparing whole records reset spoil timers on every save.
- The `Clothing` list holds the outfit plus other worn pieces such as the Rebreather. The outfit picker changes only the first outfit entry and keeps the rest, and no outfit listed means the starting Tactical Jacket (`495`). `PlayerPageViewModel.WornItemIds` feeds the map, so a worn Rebreather counts as owned.
- Tools only change the in-memory JSON and return a message for the snackbar; nothing reaches the disk until Save. The Item Plater and Unlocks are the exceptions and say so: the Plater saves at once, Unlocks edits the profile file directly after its own backup. Unlocks edits `PlayerProfile.json` of the Steam account that owns the open savegame, writes nothing when no toggle changed, and adds a missing setting only when it is on.
- Cannibal Anger is one tool with a dialog (`CannibalAngerDialog`) that sets a level from 0 to 100% in steps of 1. `SetCannibalAnger` gives every living cannibal (`ActorType.IsCannibal`, not `StateDead`) a Player influence of exactly that anger and its negative as sentiment, both ways, through `ModifyActors`, so the NPCs page lights up. A cannibal without a memory or Player influence gets one, the way the NPC dialog adds them (842 on a day 39 save); Fear and other influences stay. At 0 it also resets kills, kills per day, cut trees and village visits. Its card says it in one line, the dialog explains the rest (`CannibalAngerDialogText`). The dialog reads `CannibalMood` once: it starts at the current average, shows Now N% On Average (also at the bottom left of its tool card), and disables Apply while that level would change nothing. A raise to 30 survived a game load and save (seen in a real save); calming and strangers are untested in game.
- Big actions ask first with one sentence of explanation: every tool, Fill All Storages, Apply to All of Same Type, Remove All, Set All to Remove, Remove All Copies, Remove Copy and Delete Backup. Pages use `EditorPageBase.ConfirmAsync`.
- Teleport and spawning edit the save, so they work with the game closed.

## Navigation

- The left menu holds every page, Tools included (`/Tools`), in groups split by a thin divider (`s_pageGroups`): Savegames; Player, Inventory, Followers; Storage, Structures, NPCs, Map; Game, Tools. The Save dialog lists pages in the same order. On a client save the world pages (Storage, Followers, Game, NPCs, Structures) are disabled there too (`PageLink.NeedsWorld`), and a caption under the menu says why, because a disabled control gets no tooltip.
- The app bar holds the title with Language and Help 24 px after it on the left, and Backups, Reload and Save on the right, Save last at the edge; buttons sit 8 px apart and are disabled with no savegame, Save also while nothing is unsaved. It shows no savegame name (the owner's pick): the open savegame is the Savegames card with the Open chip and the accent ring. There is no close button: opening another savegame replaces it.
- The Tools page lists each tool as a card: its icon, bold title and chip share one row centred on one line, the one-sentence description starts under the title (`pl-9`), and the chip sits on the right: **Needs Save** (most), **Saves at Once** in amber (Item Plater, Unlocks), or **Host Save Only** greyed out for world tools on a client save. A tool that sets a level shows where it stands at the card's bottom left in blue (`Tools.ValueOf`, only Cannibal Anger so far). A hint at the top says tools need Save like any other edit.
- Help holds GitHub, **Check for Updates** and About. When a newer version was found, a red dot leads the way until the app restarts, so a dismissed update dialog is not forgotten: a `MudBadge` on Help, then the `update-dot` class on Check for Updates, which draws the same dot after its text.
- The left menu shows an amber dot on every page with changes (`MainViewModel.HasChanges(route)`), at once: `EditorPageBase` implements `IHandleEvent` and calls `MainViewModel.NotifyChanged` after each of its own UI events, which re-renders the layout. Only events do this, so scrolling a list never re-renders the layout. Every component that edits values inherits it: the pages, `FollowerPanel` and `GenericSettingEditor`. The Map page sets `EditsSavegame` to false, its camera, filters and selection change nothing; zipline edits call `NotifyChanged` from `MapViewModel`.
- Map has a menu dot for a moved, new or removed zipline (`SavegameStore.HasModified(ZipLineManagerSaveData)`), the one map edit that belongs to no other page.
- Tools gets its dot from `MainViewModel.FinishTool`, which the Tools page calls after every tool with `ToolState` from before it: the tool's card gets a `ChangedBadge` when the unsaved files or game state values moved and real changes remain, and the menu dot follows the cards. Both clear on every load or save. Set to Endgame and Reset Containers light the Game page too. A tool that moved anything also moves `MainViewModel.Revision`, so the map builds its points again (a World Item Cloner copy shows on the next visit).

## Change Dots

A small amber dot marks every value that differs from what was loaded from disk, and saving clears them all.

- Each page view model remembers its values when a save is loaded and answers `IsChanged(...)` per value and `HasChanges` for the page. Named values (player, followers, NPCs, game state and weather) go through `LoadedValues`; list entries that keep their object (armour pieces, inventory items, storages) are keyed by reference; structures need no memory, a set modification or new type is the change. `LoadedValues.Format` formats every value the same way, floats invariant, items and outfits by id, positions with their area.
- A dot sits on the field that changed, never on a picture or a title. `ChangedBadge` puts it on the top right corner of an input (`MudBadge` with `Color.Warning`); `ChangedDot` puts it at the top right of a text: menu items, switch and checkbox labels, list rows and names, before any info button. Every dot is MudBadge's 9 px; `.changed-dot` uses the same size and aligns to the top of the line (`vertical-align: top`, and `align-self: flex-start` inside the flex label of a menu button). `StatSlider`, `GenericSettingEditor` and `ItemLabel` take a `Changed` parameter; `ItemLabel` shows it after the name.
- Where the dot goes: armour on its Type select for a new piece or another type (a piece worn from the inventory is new, not just edited) and on its durability field for a changed durability (`ArmorPageViewModel.IsTypeChanged`, `IsDurabilityChanged`), a backpack armour row on its count text, storage slots on the count field, structures on the Modification button (the Percent Done column shows the loaded value in green, an arrow and what saving writes in amber, `ScrewStructureWrapper.NewPctDone`), NPCs on the name in the list and in the table on the name, or on the Unique ID while every row has one type and the Name column is gone, influences on each Sentiment, Anger and Fear field (`FollowerPageViewModel.IsChanged(follower, influence, property)`, remembered per influence type).
- Followers and NPCs reload after every actor change (`ModifyActors`), so they remember values only when the savegame object itself changes. A real load or a save creates a new one, an actor change does not. An actor change also keeps the copy each follower panel shows. Revive writes the death flags straight into the save, so it refreshes those two Game State rows (`RefreshDeathFlags`).
- Game setup switches and selects go through `SetBool` and `SetString` with the setting's default: a setting the save lacked that goes back to its default is left out again, or switching one on and off lit the Game menu and saved a new entry.
- A blueprint page in `PlayerState` changes only for a blueprint added or removed on the Inventory page, never to match the inventory on every save.
- With no savegame open nothing has changed, so `MainViewModel.HasChanges` answers false before asking any page; a page that never loaded counts every value as new.
- A dot is computed by whoever renders it. An edit inside `GenericSettingEditor` or `FollowerPanel` re-renders the page through `NotifyChanged`, so a plain `Changed` bool from the page stays fresh. `InfluencesEditor` builds its sliders itself, so it takes `ChangedWhen` (influence and property), and `FollowerPanel` passes `OnChanged` so its own handler runs and the menu follows.
- Storage compares each slot by item, food state and count (`StoragePageViewModel.ValueOf`): every food state shares one item id, so a rack slot switched from fresh to dried fish showed no dot.
- Inventory marks the count, not the picture: the dot sits on the count field, and an item removed since the load shows it in the count column where its count was, centred on the row (`ChangedDot Centered`), because it stands alone there.
- Decimal fields show two decimals, so typing back the shown value (`39,35` for `39,3456`) is a real change and keeps its dot.
- Clicking a day on the season bar moves the offset the short way from the loaded offset (`SeasonCalendar.OffsetForDay` from `WeatherPageViewModel.LoadedOffset`, never from the edited one, or a few picks round the year added whole years and a pick back still showed a change), and the loaded day brings the loaded offset back exactly, fractional or not, so its dot goes away. The New label above the picked day carries the dot.
- Tools that only touch the world JSON (fires, traps, containers, anger) have no field to mark.
- Removed entries (an armour piece, an influence) have nothing left to mark, so they show only in the menu dot and the save summary.
- To check the dots, sweep the app over CDP: per page change every input, select and switch, check its dot and the menu dot appear at once, put the value back and check both go. Filters, map layers, the copy picker and tool inputs get none. Count inside a virtualized table per row, not per page, and with no save open count the disabled menu buttons too, not just links. Type into number fields with CDP `Input.insertText` and Tab: a value set from script stays on screen above its Max, real typing clamps it. A decimal field put back as its two shown decimals keeps its dot, as described above.

## Text

- Editor text is `Resources/SharedResource.resx` (English, the neutral resx) and one `SharedResource.<culture>.resx` for every other language: `de`, `fr`, `nl`, `tr`. Every file holds the same keys with the same placeholders, none empty, or `Tests/SaveRoundTrip.cs` fails. Pages and services alike read them through `AppText` (`Get`, `Format`); there is no `IStringLocalizer`.
- `AppText.Languages` lists the shipped languages, each named in its own language and sorted by that name (Deutsch, English, Français, Nederlands, Türkçe). The picker, `AppCulture.Apply` and the Debug key check read it, and a saved language that is not shipped falls back to `AppText.DefaultCulture`, English. A new language is a resx with every key plus a line in that list.
- One word per idea in every language: savegame is Spielstand, partie, kayıt; backup Backup, copie de secours, yedek; storage Lager, rangement, depo; follower Begleiter, compagnon, yoldaş; structure Bauwerk, construction, yapı; zipline Seilrutsche, tyrolienne, zipline; item Gegenstand, objet, eşya; NPC NPC, PNJ, NPC; host Host, hôte, kurucu. German speaks as du, French as vous, Turkish sentences as siz with bare verbs on buttons, Dutch as je. French puts a no-break space before a colon or a percent sign. Turkish keeps a name placeholder plain behind a colon (Canlandırıldı: {0}), because its case endings follow the name.
- A label stays on one line at 1600 x 845 in every language: long ones were cut down until they fit (Max. Gesundheit, Alle auf Max, Akteur-ID, Tout Remplir, Vergulden). At 1280 x 680 tool card titles wrap in every language, English included.
- Search text is lowered with `ToLowerInvariant` (`Item`, `MapFilter`, `BasePoi`), so a Turkish Windows still finds Item as item.
- `AppText.Culture` is the one source of the language. The WPF dispatcher keeps the startup thread culture, so setting `CultureInfo` does nothing; every lookup passes `AppText.Culture` instead. English is the default, the `LanguagePicker` in the app bar switches and saves it.
- Item, creature and structure names stay English in every language, in `GameNames.resx`, because the game shows them in English.
- Labels are short Title Case. Longer sentences (hints, info, warnings, snackbar messages) are sentence case, short, and never end in a symbol; with two sentences only the last goes without a full stop.

- A count in a list, a group title, an option or a change line sits after the name, greyed (`mud-text-secondary`), on the right where the row has room, never in brackets: NPC rows and family titles, storage rows (`IStorage.TotalStored`, the header shows it after the name like the NPC header), map groups (`IPoiGrouper.Count`), Regrow Trees options, the actor dialog's Apply To buttons (Family 12) and repeated changes in the Save and Restore dialogs (`Change.Count`). `GroupTitle` draws a list's group title with its count, both underlined. - A field or section that needs explaining gets a blue `InfoIcon` (a plain `Icons.Material.Rounded.Info` in a tooltip, with a soft wide drop shadow and a small left margin), not a caption and never a button, so it has no hover or press; the Current Health warning uses the same icon. `Header` takes `Info`, `StatSlider` takes `Info`, and the Game tab puts one beside every setup setting. Their keys are the label key plus `Info` (`EnemyHealthInfo`). Game State and Weather rows get theirs from `TextKeys.SettingInfo` for the names in `TextKeys.SettingsWithInfo`.
- Keys built at runtime (`Item12`, `ActorType9`, `StructureCategoryTreeShelter`, `SettingGameDaysInfo`) come only from `TextKeys`. A Debug start checks every one against the game data and asserts on any missing key, so a new item, enum value or info field needs its key in both files.
- Numbers follow the Windows number format; dates are `yyyy-MM-dd`; sizes are `Formatter.FormatSize` in MB.

## Layout

Pages with lists (Storage, NPCs, Inventory, Structures, Map, the Game state tab) fill the window and end `--page-bottom` above it, through the `page-fill`, `fill`, `fill-column` and `fit` classes in `SoTF.Editor.css`. Never size a panel with a `%` or `vh` height; it misses the bottom margin. A `MudTabs` fills the page while the open tab's root carries `fill`; its other tabs scroll with the page. Lists and tables are `fit`: they shrink to their rows and stop at the bottom margin, and an empty table says Nothing Found (`NoRecordsContent`). A list page shows its pick only while the list shows it: a search that hides it, or switching NPCs between By Type and By Family, empties the main panel (NPCs, Storage, Structures). Those three work out their shown rows once per render, one local list for the empty check, the rows and the pick.

Lists and tables run edge to edge in their panel: the paper carries `panel-flush` (no padding, clipped corners, and a table inside is square so a hovered last row fills the rounded corner) and each row, group title or toolbar carries its own `px-4`. A new list follows that, never a padded paper around an inset list.

The last table row has no bottom line. A table whose rows virtualize keeps its columns with `fixed-columns` and a `ColGroup`, or the columns shift while scrolling.

## Updates

`Updater.CheckAsync` reads the `releases/latest` redirect and returns the tag and version. It runs on every start (there is no setting) and from **Help → Updates → Check for Updates**; a newer version opens `UpdateDialog` and sets the red dot on Help. The dialog lists every commit title since the installed build under What Changed, newest first and each once: the old tags are deleted, so a workflow build carries its commit instead (`AssemblyMetadata` Commit from `GITHUB_SHA`, read by `AppInfo.Commit`), and the GitHub compare API (`AppInfo.CompareApiUrl`, no token) lists the commits from it to the new tag. A build without one (Debug, local) shows the release body (`AppInfo.ReleaseApiUrl`); no notes just hide the list. Installs of 3.7 and older still read only the newest body, their dialog shipped before this. Update Now asks to discard unsaved edits and hides the dialog's X and Escape until the download fails or the window closes (`UpdateDialog.SetClosableAsync`); meanwhile `MainWindow.IsUpdating` makes closing the window explain that it closes by itself, and the dialog shows a progress bar with MB of MB and the percentage, redrawn once per percent (`Updater.DownloadAsync` reports every chunk), or an indeterminate bar while GitHub sends no length, `Updater.DownloadAsync` runs on the thread pool (`Task.Run`), so the window never stops responding, logs how long it took, and saves `SoTF.Editor_<tag>.exe` beside the running exe from the tag's asset URL (so `v1.5.1` works too), through a `.download` file that must match the asset's SHA-256 `digest` from the GitHub API first (`Updater.ExpectedDigestAsync`); a mismatch or a missing digest (`InvalidDataException`) never runs and opens the release page instead, `Updater.Launch` starts it with `--after-update <pid>`, and the window closes without asking (`MainWindow.ClosesWithoutAsking`). The new exe calls `Updater.FinishPreviousVersion` before the single-instance check: it waits up to 15 s for the old process and deletes every other `SoTF.Editor_v*.exe` beside it. A protected folder such as Program Files (`UnauthorizedAccessException`) says so and opens the release page. A Debug build or a renamed exe (`Updater.CanInstall` false) opens the release page instead. Build with `-p:Version=0.9` and use Check for Updates to see the dialog, with `GITHUB_SHA` set to an older pushed commit for the full list.

## Looks Wrong, Is Not

- `WebResourceRequested` answers only `https://files.local/` (`LocalFiles`), and only for `.png` and `.jpg` files that exist and can be read; a thumbnail the game is writing gets a 404 and the card shows its placeholder. BlazorWebView routes its own requests through the same event; answering them breaks the page.
- `MainWindow` and WebView2 both use `#202020`, so the window never flashes white.
- WebView2 zoom and pinch zoom are off (`IsZoomControlEnabled`, `IsPinchZoomEnabled`): a touchpad pinch resized the whole app. The map still zooms with the wheel, it handles that itself.
- The map points are plain `<img>` in one canvas and pan and zoom in JS (`window.sotfMap` in `AppShell.js`): a map shows thousands of them. They render in a component of their own (`MapPoints`) whose only parameter is `MapViewModel.PointsVersion`, so a pick, the panel, a hint or any other page render skips the 3,600 icons; a build, a filter, a group toggle, a zipline edit or a moved player or follower moves the version. A new set draws 1,200 icons per frame, so Select All paints at once instead of blocking. The picked point draws again on top in an overlay with its ring (`BasePoi.IconZIndex` keeps the layer's order). Measured in Chromium against 3.7.1: Select All 837 to 596 ms (blocking 281 to 15), a click on a stack 312 to 145, a zoomed point click 111 to 64, the map opening 198 to 156, a zoom button 187 to 126.
- Points stay between visits while nothing they show changed: the same `MainViewModel.Revision` (a reload, an actor change, a reverted map or tool, a tool that moved anything), the same structure types and the same owned items (`PoiLoader.OwnedItemIds`). Old points hold JSON that is no longer saved, so a new savegame releases them (`MapViewModel.ReleaseIfStale`). `PoiLoader` parses the static `Pois.json` and `ItemPois.json` only once. `VisiblePois` keeps its order: each icon's inline `z-index` does the stacking, and sorting moved the selected point to the end, which re-rendered every point after it. The JS blocks native image dragging and ends a drag on `pointercancel`, or the map follows the cursor after a press on a point. Leaving the map calls `MapViewModel.Close`, which ends a pick and keeps the points, and the next pointer move drops the old canvas in JS once it left the page. `Map.Dispose` never calls JS: awaiting JS while the window closes can hang the shutdown.
- Map points carry no drop shadow. A filter on every icon repainted them on each pan frame: with all 3,200 points panning ran at 30 fps, without it at 60. Promoting the canvas to its own layer while dragging made it worse. Every icon reads `--map-zoom` in its transform, so changing it restyles all of them (about 50 ms with every group on). Past 1,500 points a glide or wheel zoom only moves the canvas and sets `--map-zoom` 150 ms after the map settles, so icons catch up once: twelve steps went from 7 slow frames to 1. Chrome already skips the restyle while panning, because the value does not change.
- The map picture is `dark.webp` (1.7 MB at quality 90), half the old JPEG, as sharp at twice the zoom and as quick to decode. Pictures carry no cache header on purpose: BlazorWebView answers every file with no-store, yet Chromium asks for each picture once per page load (checked over eight map visits), and a kept map `Image` saved nothing either.
- Snackbars stop at 92% opacity (`MaximumOpacity`, the owner's pick: barely see-through) and fade in 200 ms, out 250 ms; the defaults, a linear 1 s in and 2 s out, looked half see-through for seconds.
- The zoom buttons and the point details panel share the `map-overlay` glass; plain filled buttons were 12% grey and vanished over the map.
- MudBlazor draws a slider thumb as a 2 px circle scaled six times, which rasterizes lopsided at 125% scaling and looked halved while dragging. `SoTF.Editor.css` gives it a real 12 px size and an 8 px halo. Sliders carry no `ValueLabel`: their label already shows the value, and the bubble covered it at the left end.
- `.mud-table-container` inherits the table's background. At 125% scaling Chrome repaints a transparent scroller on every frame and only composites an opaque one, so Inventory and Structures scrolled at 30 fps; the paper lists were already opaque.
- `PoiDetails` calls `OnMapChanged` after closing or removing, because a child's event only re-renders the child and the map page would keep the old overlay.
